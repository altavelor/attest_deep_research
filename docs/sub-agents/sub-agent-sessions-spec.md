## 1. Цель

Каждый ChatSessionRuntime владеет одним изолированным менеджером дочерних сессий.
Thinking, будущий Deep Research и map_sources используют его без отдельного глобального
реестра. Основной чат показывает из дочерней активности команды, отправленные агентам, и
компактные уведомления об их жизненном цикле. Наблюдение за работой и пользовательская
остановка доступны в модальном окне.

## 2. Принятые решения

1. «Активный» для счётчика и верхней группы списка — ровно status=running.
   queued, importing, stopping и ready не увеличивают счётчик. Это уточнение пользователя.
   «Живая» для остановки — у сессии есть активный run (queued/running/stopping) или pending
   import, а владеющий им родительский запуск ещё не terminal (решение 16).
2. Если в этом чате никогда не принимался запуск дочернего агента, кнопка скрыта.
   После первого принятого запуска она остаётся доступной сразу справа от селектора режима:
   серые иконка и 0 при отсутствии running, иначе зелёные иконка и точное число; фон всегда
   серый и светлеет при hover. Серый не означает disabled: доступна история и очередь.
   Создание сессии без запуска само по себе кнопку не показывает.
3. Вне debug lifetime показывает заголовки и статусы инструментов по правилам основного
   timeline; в debug — также безопасные входы и результаты. Вторая секция не скрывается.
4. Выжимка задачи формируется без LLM, по существующему inferChatTitle из
   src/core/chat/savedChat.ts: первая задача, пробельные символы в одну строку,
   до 80 символов, при превышении первые 77 и «...». Это уточнение пользователя.
   Общая pure-политика выделяется для обоих потребителей без изменения имён чатов.
5. Основной transcript получает исходящие initial/follow-up/retry/continue-partial команды
   и компактные уведомления: created/queued, not-started, finished (с ответом агента),
   partial, failed, stopped, interrupted, import-failed, closed и одну строку на
   batch map_sources. Он не получает child tool calls, фазы, progress, debug In/Out, child
   reasoning и внешний вывод run_subagent. Уведомления — только отображение, модели не
   отправляются. Обычные сообщения пользователя, ответ родительской модели и собственные
   инструменты родителя сохраняются. Макеты — M6 и M7 приложения шага 10.
6. Родительская модель получает импортированный ответ ребёнка для синтеза, даже когда
   этот ответ не является отдельным UI-сообщением. UI-проекция и model history различны.
7. Пользователь останавливает сессию через отдельную chat-scoped stop-only capability.
   Старый абсолютный запрет UI mutation заменён этим единственным исключением.
   UI не получает facade основной модели и не может создавать/продолжать/retry агентов.
8. Один modal содержит список и экран деталей с возвратом назад; вложенная модалка
   для перехода к сессии не открывается. Закрытие окна не останавливает выполнение.
9. Initial prompt — снимок сообщений первого запроса модели выбранного запуска после
   сборки system framing/задачи/доступного контекста, до обращения к провайдеру.
   Показ только после удаления секретов; это не reasoning и не chain-of-thought.
10. Все workers map_sources также наблюдаемы и учитываются в счётчике. Для этого выделен
    отдельный шаг миграции; ограничения, порядок строк и отдельная telemetry сохраняются.
11. Общий renderer используется обоими окнами. Копирование workflow DOM-логики запрещено;
    перенос существующего renderer без изменения поведения предшествует новым consumers.
12. Состояние дочерних сессий — optional поле subAgents того же файла чата v4; версия
    схемы не повышается. Добавляются только optional поля: subAgents, а по шагу 8 —
    subAgentDispatches, subAgentNotices, timelineSequence и ChatDisplayMessage.timelineSequence;
    существующие поля сообщений не меняются.
    Старые v2/v3/v4 чаты читаются; исторические nested child tool calls скрываются при
    показе основного окна, но не удаляются разрушительно из сохранённых файлов.

13. Делегирование асинхронно: run/continue/retry подтверждают durable приём команды
    и возвращают SubAgentRunReceipt, не ожидая исполнения. Родитель продолжает независимую
    работу; результат доступен отдельно после import. Это уточнение пользователя.
14. Пользовательская остановка проверяет expectedRunId, а не revision прогресса.
    Смена новой попытки делает старую кнопку stale; новые tool/usage события — нет.
15. Частые изменения записываются через единый для чата bounded буфер, общий с сохранением
    самого чата: сброс по времени, числу обновлений
    или объёму. Команды, начала внешних действий, terminal/cancellation и import/budget
    barriers подтверждаются только после обязательной записи. UI не ждёт сброса прогресса.

16. Сессии принадлежат чату и продолжаются любым более поздним родительским запуском того же
    чата (уточнение пользователя). Доступ к сессии (ownedRecord) проверяет только
    chatSessionId сессии и привязку store к чату; вызывающий по-прежнему проходит authorizeCall:
    текущий nonterminal parent run, совпадающая generation, зарегистрированный grant, свежий
    delivery epoch и правила budget port; чужая/отсутствующая сессия — неразличимый
    not-authorized. Новый run (follow-up/continue-partial/retry) получает parentRunId и
    bindingGeneration вызывающего запуска; сессия переносит на них свои parentRunId и
    bindingGeneration («текущий владелец»), поэтому dispatch/notice попадают в текущий ответ,
    а close/stop/fences старого запуска на неё больше не действуют. Parent terminal (closeAll)
    и startup recovery больше не архивируют: nonterminal run становится interrupted, pending
    import получает tombstone, сессия с прерванной работой — interrupted (доступны retry и
    continue-partial), бездействующая сохраняет ready/failed/interrupted. Notices interrupted
    и closed (closedCount — число затронутых неархивных сессий запуска) не изменились.
    archived остаётся только за пользовательской остановкой, stop-import и checkpoint-corrupt
    и не открывается снова. Схема не меняется: старые чаты с archived читаются как есть.
    Системный prompt родителя с инструментом run_subagent получает компактный раздел
    существующих сессий чата: sessionId · заголовок · состояние · последний run/attempt
    (только поля хоста, без текста ответа ребёнка; не больше 20 новейших, заголовки
    очищаются и ограничиваются; сессии workers map_sources, чей первый run имеет origin
    map_sources, не перечисляются), без сессий раздел не выводится. Лимит одновременных
    runs (4, FIFO) и бюджеты сессий не меняются.

Отклонены: отдельный plugin-wide manager (утечка владения между чатами), управление через
model facade из UI (расширение прав), второй renderer (расхождение debug/lifecycle),
LLM-суммаризация заголовков (не соответствует уточнению и добавляет запросы).

## 3. Сквозные правила

- apps → adapters → application → core; core без I/O, DOM, Node и Obsidian.
- Runtime создаёт manager через внедрённую фабрику ровно один раз и сам освобождает его.
  Общие top-level шесть слотов не используются как реестр или очередь дочерних запусков.
- Session принадлежит чату (решение 16); её parentRunId/bindingGeneration — последний
  родительский запуск, поставивший run. Run имеет отдельный ID/attempt и свой parentRunId.
  Один ребёнок выполняет не больше одного run. Контекст bounded, рекурсия и mutation запрещены.
- Нормальное завершение runner означает importing; ready и публичный успех только после
  durable import. Receipt команды не означает успех исполнения. Binding и delivery epoch различны; старый epoch не доставляет события.
- Manager/chat/budget serializers не ожидают друг друга. Fences выставляются синхронно;
  внешние async-операции идут off-lock, результаты применяются через CAS полной идентичности.
- Parent terminal до публикации terminal и освобождения слота прерывает активные runs и
  pending imports своих сессий и отзывает binding/grants; сессии остаются продолжаемыми.
  View/modal close и переключение чатов не являются parent terminal.
- Все записи живут столько же, сколько чат; рост ограничен размером, не временем: подробности
  не более 2 MiB на чат, старые terminal-запуски вытесняются, хранятся последние три context
  summaries. Цитируемые evidence сохраняются.
  Debug off запрещает захват новых payload, debug on не восстанавливает отсутствующие данные.
- Ни один UI-путь, persistence DTO или экспорт не содержит секретов/credentials/child CoT.
  Текст задач и внешние результаты недоверенные: redaction, ограничения, безопасный текстовый DOM.
- Неполные usage-поля показываются как «нет данных»/«частично», а не выдуманный ноль.
  Reasoning/cache tokens не складываются второй раз с уже включающими их итогами.
- Локализация всех новых UI-строк через существующий i18n; русский язык документов не меняет
  язык приложения. Учитывать Mobile, keyboard, RTL, длинные тексты, пустое состояние и ошибки.
- Все критерии шага привязаны к обозначенным в нём тестам U/S либо live-проверке L.
  U=tests/unit, S=tests/scenario. Правило проверяется единожды на подходящем уровне.
  Изменившееся поведение редактирует старый тест, а не добавляет дубль.
- Выполнение шагов включает npm ci и npm run check перед публикацией; тестовые лимиты,
  case density 0.2/branch и mutation-проверки удаляемых групп следуют AGENTS.md.
  На реализации запускать npm run test:coverage и npm run test:growth -- origin/main.
  Новые shared fakes только tests/support; дедлайны — fake clock, ожидания — settle/eventually.
- Числа лимитов в шагах нормативны, а не иллюстративны. Примеры ID иллюстративны.

## 4. Порядок работ и независимость шагов

Контракты предшествуют хранению и менеджеру, budgets и import — production-интеграции.
Шаги 1–6 поставляют не подключённые к текущему UI модули с injected ports/fakes;
существующий stateless путь продолжает работать. Шаг 7 сохраняет parent rendering.
Шаг 8 переключает прямую делегацию, шаг 9 — map_sources, шаг 10 подключает UI.
Каждый шаг отдельно проверяем и оставляет приложение работоспособным.
До завершения шага 9 stateless execution port сохраняется только для map_sources.

Сохранённые обязательства старой спецификации:

| Область исходника                                                   | Где нормативно раскрыта |
| ------------------------------------------------------------------- | ----------------------- |
| State model, source subset, retry lineage                           | Шаг 1                   |
| Секция subAgents чата, v2/v3/v4, хранение/recovery                  | Шаг 2                   |
| Ownership, binding, local lifecycle, stable create                  | Шаг 3                   |
| Registration, permits, typed closure, cleanup CAS                   | Шаг 4                   |
| Generations, tombstones, aliases, delivery epochs                   | Шаг 5                   |
| Usage, безопасный prompt/tool log, пользовательская stop capability | Шаг 6                   |
| Shared renderer/debug, lifecycle DOM                                | Шаг 7                   |
| Parent lifecycle/Thinking и только исходящие сообщения в main       | Шаг 8                   |
| Ограничения и отдельная telemetry map_sources                       | Шаг 9                   |
| Modal list/detail, счётчик и stop                                   | Шаг 10                  |

## 5. Что не делается

Deep Research plan/review/gather/verify/synthesize/export как самостоятельный режим;
редактирование prompt пользователем; самостоятельный чат с ребёнком; UI retry/continue;
перенос агента между чатами; общие живые агенты; рекурсия; mutation заметок; стоимость;
новые зависимости; глобальное ограничение мощности; работа при закрытом Obsidian;
синхронизация живых сессий между устройствами. Эти функции не блокируют данный комплект.

Открытых продуктовых вопросов после уточнений пользователя нет.
Техническая непроверенная область: фактическая длительность и плотность будущих тестов.
Она проверяется на реализации каждого шага по AGENTS.md; план роста — бюджет, не отчёт
о запущенных тестах. Превышение требует уменьшить/разделить fixture/case, не повысить лимиты.
Асинхронный tool-result является намеренным изменением будущего wire-контракта:
run_subagent возвращает receipt; map_sources запускает batch и отдаёт matrix через
get_map_sources_result. Старые сохранённые результаты читаются как legacy, не переисполняются.
Recovered Deep Research draft при будущей реализации должен потреблять этот контракт.
Внешний вид задан [макетами шага 10](sub-agent-sessions-step-10-mockups.md) и проверяется
live по шагу 10; утверждение спецификации не разрешает
реализацию Deep Research целиком.
