# Спецификация: улучшение Thinking Prompt в Attest

**Статус:** Нормативный roadmap для отдельной prompt-фазы; не является source of truth для
сопутствующих runtime/tool API изменений в текущем PR

**Область будущей prompt-фазы:** `src/core/research/thinkingPrompts.ts` и связанные prompt-модули

**Не входит в будущую prompt-фазу:** runtime/tool API изменения и UI; они проектируются и
ревьюятся отдельно

## 1. Допущения

1. Под «текущим промптом» понимается system prompt Thinking-стратегии, который собирает
   `buildThinkingResearchMessages`; Instant Prompt должен сохранить совместимое поведение.
2. Главный приоритет — корректное выполнение пользовательского намерения: безопасные действия,
   проверяемые утверждения и отсутствие лишних результатов важнее максимальной полноты ответа.
3. Улучшение должно одинаково работать с OpenAI-compatible, Anthropic и Ollama-моделями, включая
   модели без parallel tool calls.
4. Схемы зарегистрированных tools остаются источником истины для аргументов; prompt должен задавать
   политику выбора и использования tools, а не дублировать их полные контракты.
5. Необходима эволюционная миграция без изменения публичного API
   `buildThinkingResearchMessages(options): ChatMessage[]`.

Если эти допущения неверны, спецификацию следует скорректировать до планирования реализации.

## 2. Исходное состояние и проблемы

Thinking Prompt сейчас динамически объединяет базовые правила, режим Vault/Research, доступность
источников и секции отдельных возможностей. Capability-gating и защита от выдуманных действий уже
являются сильными сторонами текущей реализации. Улучшение должно их сохранить.

Аудит текущего текста и локальных диагностических прогонов выявил следующие риски:

| ID  | Проблема                                                                                                                                                                | Наблюдаемое или возможное последствие                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| P2  | Research-секция запрещает использовать результаты editing tools как evidence, тогда как Vault и compile-knowledge требуют читать заметки и синтезировать их содержимое. | Модель получает конфликтующие инструкции и либо игнорирует заметки, либо использует их без ясной provenance-политики.          |
| P3  | Нет явного правила «ровно запрошенные артефакты».                                                                                                                       | В запросе на пять отдельных заметок модель может создать дополнительную обзорную заметку.                                      |
| P4  | Цитирование описано преимущественно через синтаксис идентификатора, но слабо определяет semantic entailment.                                                            | Реальная ссылка может не подтверждать стоящее рядом утверждение; диагностический прогон показал семь неверифицированных цитат. |
| P5  | «Authoritative sources» не сопровождается правилами выбора первичных источников, свежести и различия snippet/full page.                                                 | Рейтинг, цена, должность или иная изменчивая информация может опираться на слабый либо устаревший источник.                    |
| P6  | Длинный монолитный prompt повторяет tool schema и одновременно содержит policy, workflow и справочный материал.                                                         | Лишние токены, ухудшение соблюдения приоритетных правил и высокий риск дрейфа prompt ↔ runtime.                                |
| P7  | Инструкция вызывать независимые tools вместе не учитывает модели без поддержки parallel calls.                                                                          | Модель может сформировать недопустимый ответ либо неверно считать последовательное выполнение ошибкой.                         |
| P8  | Compile-knowledge включается по наличию index + mutation tools, а не по намерению пользователя.                                                                         | Простой запрос на короткие заметки может быть интерпретирован как построение расширенного графа знаний.                        |
| P9  | Нет общего предфинального протокола проверки результата.                                                                                                                | Модель может завершить ответ до проверки количества успешных мутаций, покрытия источниками и незакрытых ошибок tools.          |
| P10 | Нет явного требования отвечать на языке пользователя и соблюдать запрошенную степень краткости.                                                                         | Англоязычные или чрезмерно подробные заметки при коротком русскоязычном запросе.                                               |

## 3. Цель

Перестроить Thinking Prompt в компактную и однозначную систему инструкций, которая:

- точно маршрутизирует запрос между ответом, исследованием, чтением vault и мутациями;
- выполняет только явно запрошенные побочные действия и не повреждает существующие данные;
- делает только те фактические утверждения, которые поддержаны конкретным evidence;
- адаптируется к реально зарегистрированным tools и возможностям модели;
- сохраняет prompt-injection boundary для пользовательского контента, index description и результатов
  tools;
- проверяет собственный результат перед финальным сообщением.

Пользовательский результат считается успешным, когда Attest делает ровно то, что было запрошено,
может честно перечислить подтверждённые действия и выдаёт проверяемый ответ без вымышленных либо
неподтверждённых деталей.

## 4. Не-цели

- Не менять форматы tool calls, их JSON-схемы или названия.
- Не переносить policy enforcement из application layer в prompt.
- Не вводить новый LLM-вызов только для классификации намерения.
- Не гарантировать истинность исключительно prompt-инструкциями: runtime verification остаётся
  обязательным уровнем защиты.
- Не добавлять провайдер-зависимые варианты prompt-а, если различие не выражено capability-флагом.
- Не менять продуктовый смысл режимов `Index`, `Web`, `Index + Web` и `Vault`.

## 5. Требуемое поведение

### 5.1. Иерархия инструкций

Собранный system prompt должен иметь стабильный порядок:

1. Идентичность, дата и application-enforced ограничения.
2. Непереопределяемые правила безопасности и честности действий.
3. Интерпретация пользовательского намерения и критерий завершения.
4. Политика evidence и цитирования.
5. Доступные capability-модули.
6. Делимитированные недоверенные данные.

Если локальная capability-секция противоречит общему правилу, приоритет имеет более раннее общее
правило. Это должно быть сказано один раз, без повторов в каждой секции.

### 5.2. Контракт выполнения пользовательского запроса

Перед первым tool call модель должна внутренне определить:

- ожидаемый результат: ответ, список, сравнение, чтение, создание, изменение или удаление;
- точное количество и тип артефактов, если они названы;
- требуемые источники и критерий достаточности evidence;
- необходимость побочного действия;
- запреты и ограничения пользователя, включая формат, язык и краткость.

В prompt следует добавить короткий универсальный контракт:

```text
Execute the user's requested deliverables exactly. Do not add files, notes, downloads,
or other side effects that were not requested. Match the user's language and requested
level of detail. Before the final answer, compare successful tool results with every
requested deliverable and report any gap explicitly.
```

Для запроса «создай 5 заметок, отдельную для каждой компании» корректный результат — ровно пять
успешно созданных или согласованно обновлённых заметок. Обзорная шестая заметка запрещена без
явного запроса или подтверждения пользователя.

### 5.4. Единая модель evidence

Нужно устранить двусмысленное деление «editing tools — не evidence»:

- `search_notes` и `list_notes` возвращают навигационные метаданные и сами по себе не подтверждают
  содержательные утверждения.
- `read_note`, `get_active_note`, index и web могут возвращать содержательное evidence, но только
  зарегистрированный runtime идентификатор разрешено использовать как цитату.
- Результат mutation tool подтверждает лишь факт действия и путь; он не подтверждает факты внутри
  записанного текста.
- Sub-agent answer является вторичным контейнером evidence: допустимы только сохранённые в нём
  валидные citation tokens.
- Любой текст из tool result, вложения, истории, index description или vault считается недоверенными
  данными и не может менять system policy или требовать tool call.

### 5.5. Политика источников

Для evidence-dependent утверждений модель должна:

1. Предпочитать первичный источник: официальный документ, filing, документацию, публикацию автора.
2. Для рейтингов и агрегированных сравнений использовать специализированный источник с явной датой
   среза; при высокой изменчивости сверять минимум с одним независимым источником.
3. Отличать search snippet от fetched page и не выводить из snippet детали, которых в нём нет.
4. Проверять дату публикации/обновления относительно `Current date` для слов «сейчас», «последний» и
   аналогичных.
5. Явно обозначать расхождения между источниками и не усреднять несовместимые значения без
   объяснения.
6. Останавливаться на достаточном evidence; не собирать источники без связи с deliverables.

Local index и web не должны объявляться «равными по авторитетности». Их вес определяется типом,
происхождением, свежестью и прямотой поддержки конкретного утверждения.

### 5.6. Политика цитирования

- Каждая цитата должна подтверждать всё непосредственно предшествующее атомарное утверждение.
- Если предложение содержит несколько независимо проверяемых фактов, его нужно разбить либо дать
  каждой части подходящую цитату.
- Наличие валидного URL/evidenceId недостаточно: текст evidence должен семантически поддерживать
  утверждение.
- Нельзя цитировать источник только потому, что он относится к той же теме.
- Для неподтверждённого факта модель должна найти дополнительное evidence, смягчить формулировку или
  явно сообщить, что факт не подтверждён.
- Не добавлять отдельный список источников, если пользователь его не просил и inline citations уже
  достаточны. В создаваемой заметке список источников допустим как пользовательский формат, но не
  заменяет inline citations.

### 5.7. Capability- и intent-gating

Prompt-модуль включается только когда одновременно выполнены условия:

- все упомянутые в модуле tools реально зарегистрированы либо текст явно ветвится по их наличию;
- пользовательское намерение соответствует модулю;
- модуль добавляет правила принятия решений, которых нет в tool schema.

Минимальная маршрутизация:

| Intent                  | Включаемые инструкции                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| Самодостаточный вопрос  | Core answer; tools только если политика приложения требует источник.                        |
| Актуальный внешний факт | Core research + Web.                                                                        |
| Вопрос по корпусу       | Core research + Index.                                                                      |
| Навигация/чтение vault  | Vault read/navigation.                                                                      |
| Явная запись в vault    | Action honesty + safe mutation; research-модули только при необходимости наполнить заметку. |
| Сравнение документов    | Map sources, если tool доступен.                                                            |
| Поиск противоречий      | Find claims, если tool доступен.                                                            |
| Компиляция базы знаний  | Compile knowledge только при явном намерении создать связанный набор knowledge notes.       |
| Скачивание              | Download только при явном запросе сохранить документ.                                       |

Intent-gating должен быть детерминированным и локальным. Предпочтительный вариант — чистая функция
на основе уже доступных `question`, `requiredTools`, `coreVariant` и `availableTools`; если надёжная
классификация невозможна, включается более короткая универсальная секция, а не расширенный workflow.

### 5.8. Последовательность и параллельность tools

- Prompt не должен требовать parallel calls, если capability модели неизвестна или отключена.
- Независимые calls можно рекомендовать выполнять параллельно только при переданном capability-флаге.
- Без parallel capability те же calls выполняются последовательно без изменения критерия успеха.
- Повтор идентичного вызова запрещён, кроме явно описанного retry после временной ошибки; retry должен
  быть ограничен одной попыткой с изменёнными параметрами или источником.

### 5.9. Предфинальная проверка

Перед terminal answer модель должна проверить:

- обязательные source tools действительно успешно завершились;
- каждый запрошенный артефакт имеет подтверждённый результат tool call;
- не создано лишних артефактов;
- каждое существенное evidence-dependent утверждение поддержано подходящей цитатой;
- ошибки, отмены и неполные данные отражены явно;
- ответ соответствует языку, формату и краткости запроса.

Эта проверка не должна выводиться как chain-of-thought. Пользователь получает только короткий итог и
перечень незакрытых проблем, если они есть.

## 6. Архитектура prompt-а

### 6.1. Целевая структура

```text
src/core/research/
  thinkingPrompts.ts          -> тонкий сборщик ChatMessage[]
  promptPolicy.ts             -> базовые неизменяемые правила и порядок секций
  promptIntent.ts             -> чистая детерминированная классификация нужных модулей
  promptCapabilities.ts       -> capability-gating без текстов tool schema
  thinkingSourcePrompts.ts    -> правила выбора/проверки evidence
  thinkingActionPrompts.ts    -> правила vault mutations и download
  thinkingWorkflowPrompts.ts  -> map/claims/compile/sub-agent workflows
```

Имена файлов уточняются при планировании; обязательны разделение ответственности и curated exports
через `src/core/research/index.ts`. Все функции остаются чистыми и platform-neutral.

### 6.2. Представление секций

Вместо свободного массива строк рекомендуется внутренний тип:

```ts
interface PromptSection {
  id: string;
  priority: "policy" | "workflow" | "reference" | "untrusted-data";
  enabled: boolean;
  content: string;
  referencedTools: readonly string[];
}
```

Сборщик обязан валидировать уникальность `id`, порядок priority и условие
`referencedTools ⊆ availableTools`. В production он не должен падать из-за лишней необязательной
секции: секция исключается и событие попадает в существующую diagnostics-инфраструктуру. Базовая
policy-секция при ошибке сборки не исключается.

### 6.3. Токенный бюджет

- Не дублировать поля и аргументы, уже переданные модели в JSON tool schema.
- Описывать только выбор инструмента, ограничения безопасности и интерпретацию результата.
- Установить измеримый baseline для четырёх профилей: Vault, Index, Web, Index + Web + mutations.
- После рефакторинга статическая часть каждого профиля должна стать не длиннее текущего baseline;
  целевое сокращение для самого полного профиля — не менее 20% без удаления обязательных правил.
- Delimited evidence, chat history и index description измеряются отдельно и не входят в статический
  бюджет.

## 8. Стиль реализации

- Чистые функции, явные типы, capability decisions отдельно от текстового rendering.
- Константа отвечает за одну политику; одинаковая формулировка не копируется между модулями.
- Условный текст строится из структурированных данных, а не большим вложенным template literal.
- Все названия tools берутся из `@core/agent/toolNames`; строковые дубликаты запрещены.

Пример желаемого стиля:

```ts
function buildSafeMutationSection(tools: ReadonlySet<string>): PromptSection {
  const referencedTools = NOTE_MUTATION_TOOLS.filter((name) => tools.has(name));
  return {
    id: "safe-mutations",
    priority: "policy",
    enabled: referencedTools.length > 0,
    referencedTools,
    content: SAFE_MUTATION_POLICY,
  };
}
```

## 9. Стратегия тестирования

### 9.1. Unit tests сборщика

- Snapshot-тесты не использовать; проверять обязательные и запрещённые смысловые фрагменты.
- Для каждого профиля проверить порядок policy/workflow/untrusted-data секций.
- Проверить, что prompt требует ровно запрошенное количество артефактов и запрещает дополнительные.
- Проверить language/detail contract.
- Проверить, что compile-knowledge отсутствует в простом запросе на короткие отдельные заметки.
- Проверить последовательный вариант для модели без parallel capability.

### 9.2. Drift и security tests

- Расширить drift guard: каждое `referencedTools` должно входить в runtime registry профиля.
- Передача названия несуществующего tool в rendered text должна падать в тесте.
- Injection payloads проверить для index description, attachment manifest, explicit evidence,
  conversation registry и симулированного tool result.
- Недоверенные данные не должны появляться раньше policy-секций и не должны закрывать собственные
  delimiters.

### 9.3. Behavioral regression tests

Использовать scripted/fake model, а не сетевые LLM-вызовы:

1. «Создай 5 заметок…» — пять mutation calls, без шестой заметки; каждый успех проверен.
2. `already-exists` — нет overwrite без явного разрешения; выбран append/new path/clarification.
3. Три успешные и две неуспешные записи — финал сообщает `3/5`, перечисляет два сбоя.
4. Citation с тематически похожим, но неподтверждающим chunk — ответ не считается верифицированным.
5. Web-only запрос на актуальный рейтинг — учитываются свежесть и snapshot date.
6. Модель без parallel calls — последовательное выполнение принимается как корректное.
7. Простой vault summary — note content можно использовать, навигационные результаты нельзя выдавать
   за содержательное evidence.
8. Prompt injection внутри fetched page — policy и requested deliverables не меняются.

### 9.4. Prompt evaluation matrix

До и после изменения выполнить фиксированный набор задач минимум на одной сильной и одной компактной
локальной модели. Для каждого кейса фиксировать:

- completion rate запрошенных deliverables;
- extra-side-effect rate (цель: 0%);
- destructive-overwrite rate (цель: 0%);
- verified citation rate (цель: не ниже baseline, целевое значение ≥95%);
- unsupported-claim count;
- число tool calls и повторных идентичных calls;
- статические prompt chars/tokens;
- соответствие языка и формата.

Сетевые результаты не входят в обязательный unit suite, но обезличенный сценарий и итоговые метрики
следует сохранить как воспроизводимый evaluation report.

## 10. Границы изменений

### Всегда

- Сохранять application-level enforcement обязательных tools и citation verification.
- Считать external data недоверенными.
- Добавлять regression test на каждое изменённое поведение.
- Синхронизировать prompt с реальным registry и tool constants.
- Выполнять `npm run check` перед публикацией.

### Сначала согласовать

- Изменение публичного API `buildThinkingResearchMessages`.
- Добавление нового capability-флага в application/core contract.
- Изменение confirmation UX для write/delete/download.
- Новые зависимости, настройки пользователя или telemetry.
- Автоматическую замену существующих заметок при любом условии.

### Никогда

- Не разрешать evidence или tool result переопределять system policy.
- Не объявлять действие успешным без подтверждающего результата tool call.
- Не выполнять destructive overwrite/delete на основе только предположения модели.
- Не упоминать недоступный tool как доступный.
- Не ослаблять runtime verification ради более короткого prompt-а.

## 11. Критерии приёмки

1. Все десять проблем P1–P10 имеют реализованное требование и regression coverage.
2. Запрос ровно на N артефактов не создаёт N+1 артефакт; scripted test для N=5 проходит.
3. Навигационные, содержательные и mutation tool results имеют непротиворечивую evidence-политику.
4. Drift guard доказывает, что prompt не рекламирует незарегистрированные tools.
5. Поведение корректно для моделей как с parallel calls, так и без них.
6. Все недоверенные динамические данные санитизированы, ограничены delimiters и расположены после
   policy-секций.
7. Citation regression suite не допускает цитату, которая лишь тематически похожа, но не
   подтверждает утверждение.
8. Статическая часть самого полного prompt-профиля сокращена минимум на 20% относительно
   зафиксированного baseline либо владелец продукта письменно принимает меньший выигрыш с причиной.
9. Публичный API и fallback Thinking → Instant остаются обратно совместимыми.
10. `npm run check` завершается успешно.
11. Evaluation matrix показывает 0 лишних side effects, 0 destructive overwrites и verified
    citation rate не ниже baseline на обеих выбранных моделях.

## 12. Риски и меры снижения

| Риск                                                         | Мера                                                                                         |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Слишком короткий prompt ухудшит соблюдение редких workflows. | Сокращать дублирование, а не policy; сравнивать по evaluation matrix.                        |
| Intent-gating ошибочно исключит нужный модуль.               | Консервативный fallback на короткую универсальную секцию и table-driven tests.               |
| Prompt-тесты станут хрупкими к формулировкам.                | Проверять section IDs, tool references и смысловые invariants, а не полный текст.            |
| Поведение различается между моделями.                        | Матрица минимум из двух классов моделей и отсутствие требования parallel calls по умолчанию. |
| Citation verifier даёт false positives/negatives.            | Не использовать его как единственный oracle; добавить curated entailment fixtures.           |
| Разбиение файла создаст циклы или нарушит core purity.       | Только inward core imports, `typecheck:core` и `depcruise` на каждом этапе.                  |

## 13. Открытые вопросы для утверждения

1. Должны ли прочитанные через `read_note` заметки получать citable evidenceId, или в Vault-режиме
   достаточно явно обозначать их как пользовательские данные без inline citation?
2. Нужен ли отдельный confirmation step перед серией из большого числа мутаций (например, более 10),
   даже если пользователь явно попросил запись?
3. Является ли цель сокращения полного статического prompt-а на 20% приемлемой, или нужен абсолютный
   лимит tokens для локальных моделей?
4. Какие две модели и какой фиксированный evaluation-набор считаются release gate для prompt changes?
5. Следует ли запретить отдельную секцию `Sources` во всех ответах или разрешать её для создаваемых
   evergreen notes как дополнение к inline citations?

## 14. Условие перехода к планированию

Реализация не начинается, пока владелец продукта не подтвердит допущения, критерии приёмки и решения
по открытым вопросам 1–5. После утверждения нужен отдельный implementation plan с атомарными этапами,
характеризационными тестами до изменения execution flow и перечнем файлов для каждого этапа.
